Excellent question! Let me walk you through exactly how you'd define workloads in NRP that would be scheduled onto the Kip virtual node and burst to AWS as ephemeral instances.

Understanding the Flow
Kip runs as a pod in your NRP namespace and registers itself as a virtual node in the Nautilus cluster
You submit regular Kubernetes workloads (Pods, Jobs, Deployments) to NRP with specific selectors/annotations
Kubernetes scheduler sees these workloads need to run on the virtual node
Kip intercepts the pod creation and spins up an AWS EC2 instance
Pod runs on the ephemeral instance and is terminated when complete
Basic Pod Definition for Kip
Here's how you'd define a simple pod in NRP that bursts to AWS:

yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-gpu-job
  namespace: your-nrp-namespace  # Your NRP namespace
  labels:
    app: gpu-training
  annotations:
    # Kip-specific annotations to control the AWS instance
    pod.elotl.co/instance-type: "g4dn.xlarge"  # Optional: specify instance type
    pod.elotl.co/launch-type: "spot"           # Optional: use spot instances
    pod.elotl.co/private-ip-only: "true"       # Optional: no public IP
spec:
  # KEY: This tells Kubernetes to schedule on the Kip virtual node
  nodeSelector:
    type: virtual-kubelet
  
  # Optional: Add tolerations if Kip node has taints
  tolerations:
  - key: virtual-kubelet.io/provider
    operator: Exists
    effect: NoSchedule
  
  restartPolicy: Never  # Recommended for batch jobs
  
  containers:
  - name: gpu-workload
    image: nvidia/cuda:11.8-runtime-ubuntu22.04
    command: 
    - /bin/bash
    - -c
    - |
      echo "Starting GPU workload..."
      nvidia-smi
      python train_model.py
      echo "Job complete!"
    
    resources:
      limits:
        nvidia.com/gpu: 1      # Request GPU
        memory: "16Gi"
        cpu: "4"
      requests:
        nvidia.com/gpu: 1
        memory: "16Gi"
        cpu: "4"
    
    # Mount data from NRP storage
    volumeMounts:
    - name: training-data
      mountPath: /data
    - name: results
      mountPath: /output
  
  volumes:
  # Use NRP's Ceph storage
  - name: training-data
    persistentVolumeClaim:
      claimName: my-training-data-pvc
  - name: results
    persistentVolumeClaim:
      claimName: my-results-pvc

How It Works

Adding Kip to Multiple Namespaces
Now, here's an interesting question: Can you deploy Kip in multiple namespaces?

Option 1: Single Kip Instance (Recommended)
Deploy one Kip instance that can be used by multiple namespaces:

yaml
# Kip deployed in: ucsd-cs-shared
# Virtual node available to all ucsd-cs-* namespaces

# Users in any namespace can use it:
apiVersion: v1
kind: Pod
metadata:
  name: my-gpu-job
  namespace: ucsd-cs-vision-lab  # Different namespace
spec:
  nodeSelector:
    type: virtual-kubelet
    provider: kip
  # ... rest of pod spec
Advantages:

Single point of management
Shared AWS account and credentials
Easier cost tracking
One VPN connection to manage
Governance:

yaml
# Set resource quotas per namespace to control AWS spending
apiVersion: v1
kind: ResourceQuota
metadata:
  name: aws-burst-quota
  namespace: ucsd-cs-vision-lab
spec:
  hard:
    # Limit how many pods can burst to AWS
    count/pods: "10"
  scopeSelector:
    matchExpressions:
    - operator: In
      scopeName: PriorityClass
      values: ["aws-burst"]

3.3 Create AWS Network Infrastructure

bash
# Create VPC
VPC_ID=$(aws ec2 create-vpc \
  --cidr-block 10.200.0.0/16 \
  --tag-specifications 'ResourceType=vpc,Tags=[{Key=Name,Value=ucsd-vision-kip},{Key=Project,Value=VisionLab}]' \
  --query 'Vpc.VpcId' --output text)

echo "VPC ID: $VPC_ID"

# Enable DNS hostnames
aws ec2 modify-vpc-attribute --vpc-id $VPC_ID --enable-dns-hostnames

# Create Internet Gateway (for pulling images, etc.)
IGW_ID=$(aws ec2 create-internet-gateway \
  --tag-specifications 'ResourceType=internet-gateway,Tags=[{Key=Name,Value=ucsd-vision-kip}]' \
  --query 'InternetGateway.InternetGatewayId' --output text)

aws ec2 attach-internet-gateway --vpc-id $VPC_ID --internet-gateway-id $IGW_ID

# Create subnets in multiple AZs for redundancy
SUBNET_1=$(aws ec2 create-subnet \
  --vpc-id $VPC_ID \
  --cidr-block 10.200.1.0/24 \
  --availability-zone us-west-2a \
  --tag-specifications 'ResourceType=subnet,Tags=[{Key=Name,Value=ucsd-vision-kip-1}]' \
  --query 'Subnet.SubnetId' --output text)

SUBNET_2=$(aws ec2 create-subnet \
  --vpc-id $VPC_ID \
  --cidr-block 10.200.2.0/24 \
  --availability-zone us-west-2b \
  --tag-specifications 'ResourceType=subnet,Tags=[{Key=Name,Value=ucsd-vision-kip-2}]' \
  --query 'Subnet.SubnetId' --output text)

echo "Subnet 1: $SUBNET_1"
echo "Subnet 2: $SUBNET_2"

# Create route table
RTB_ID=$(aws ec2 create-route-table \
  --vpc-id $VPC_ID \
  --tag-specifications 'ResourceType=route-table,Tags=[{Key=Name,Value=ucsd-vision-kip}]' \
  --query 'RouteTable.RouteTableId' --output text)

# Add route to internet gateway
aws ec2 create-route \
  --route-table-id $RTB_ID \
  --destination-cidr-block 0.0.0.0/0 \
  --gateway-id $IGW_ID

# Associate route table with subnets
aws ec2 associate-route-table --subnet-id $SUBNET_1 --route-table-id $RTB_ID
aws ec2 associate-route-table --subnet-id $SUBNET_2 --route-table-id $RTB_ID

# Create security group
SG_ID=$(aws ec2 create-security-group \
  --group-name ucsd-vision-kip-cells \
  --description "Security group for Vision Lab Kip cells" \
  --vpc-id $VPC_ID \
  --tag-specifications 'ResourceType=security-group,Tags=[{Key=Name,Value=ucsd-vision-kip-cells}]' \
  --query 'GroupId' --output text)

# Allow all outbound (for downloading images, accessing S3, etc.)
aws ec2 authorize-security-group-egress \
  --group-id $SG_ID \
  --ip-permissions IpProtocol=-1,FromPort=-1,ToPort=-1,IpRanges='[{CidrIp=0.0.0.0/0}]'

# Allow inbound from NRP network (get CIDR from NRP admins)
# Example: NRP network is 100.64.0.0/16
aws ec2 authorize-security-group-ingress \
  --group-id $SG_ID \
  --protocol -1 \
  --cidr 100.64.0.0/16

# Allow internal communication between cells
aws ec2 authorize-security-group-ingress \
  --group-id $SG_ID \
  --protocol -1 \
  --source-group $SG_ID

echo "Security Group ID: $SG_ID"

# Save these IDs for later
cat > aws-infrastructure.txt << EOF
VPC_ID=$VPC_ID
SUBNET_1=$SUBNET_1
SUBNET_2=$SUBNET_2
SG_ID=$SG_ID
AWS_REGION=us-west-2
EOF

Question 1: Priority and Preemption - How Do You "Get Your Hardware Back"?
How Kubernetes Scheduling Works
Kubernetes schedules PODS (your workloads) onto NODES (machines).

When you submit a pod:

bash
kubectl apply -f my-job.yaml
# Kubernetes scheduler looks for a node with enough resources
# If found, schedules the pod there
# If not found, pod sits in "Pending" state
The "Priority" Model
NRP says "you get priority in computing on your hardware whenever you'd like" 
National Research Platform (NRP)
, but what does that actually mean?

It's implemented via PriorityClasses:

yaml
# High priority for SDSU users
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: sdsu-high-priority
value: 1000000
globalDefault: false
description: "SDSU users get priority on SDSU hardware"

---
# Low priority for opportunistic users
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: opportunistic
value: 100
preemptionPolicy: PreemptLowerPriority
description: "Opportunistic use of idle resources"
Your pod (high priority):

yaml
spec:
  priorityClassName: sdsu-high-priority
  # Your job
Random user's pod (low priority):

yaml
spec:
  priorityClassName: opportunistic
  # Their job
What Actually Happens When You Need Your Hardware Back
Scenario: All your nodes are full with low-priority jobs. You submit a high-priority job.

Step-by-step:

You submit high-priority pod (t=0s)
bash
   kubectl apply -f my-urgent-job.yaml
```

2. **Scheduler tries to find space** (t=0-2s)
   - Looks for nodes with available capacity
   - Finds none - all nodes full

3. **Scheduler initiates preemption** (t=2s)
   - Identifies low-priority pods on your hardware
   - Marks them for eviction
   - Sends SIGTERM to the containers

4. **Low-priority pods get grace period** (t=2s - t=32s)
   - Default: 30 seconds to shut down gracefully
   - Pod can save state, checkpoint, cleanup
   - After grace period: SIGKILL (forced termination)

5. **Node resources freed** (t=32s)
   - Low-priority pod removed
   - Resources available

6. **Your pod starts** (t=33s)
   - Scheduler places your pod
   - Container image pulled (if not cached)
   - Pod starts running

**Total time: ~30-60 seconds** (depending on grace period and image pull)

### The Reality: It's NOT Instant
```
Free user's job running on your hardware
↓
You submit high-priority job
↓
[30-60 second delay while eviction happens]
↓
Your job starts
```

**Problems with this model:**

1. **Not instant** - 30-60 second delay minimum
2. **Someone loses work** - The evicted pod's work is lost (unless they checkpointed)
3. **Not predictable** - You don't know which pods will be evicted
4. **Still competition** - Multiple high-priority users still compete

**This is why taints are better than priority:**

With taints:
```
Free user tries to schedule on your hardware
↓
REJECTED IMMEDIATELY (no toleration)
↓
Never even gets scheduled
↓
Your hardware stays available
```

No eviction drama, no delays, just clean access control.

## Question 2: Kip Node vs Pods - What's the Mapping?

This is where the abstraction layers get confusing! Let me clarify:

### Kubernetes Abstractions
```
NODE (physical or virtual machine)
  ↓ runs
POD (your workload - one or more containers)
  ↓ contains
CONTAINER (Docker/OCI container)
```

### Traditional Model (Physical Hardware)
```
Physical Server (NODE)
  ├─ GPU 1
  ├─ GPU 2
  ├─ 64 CPUs
  └─ 512 GB RAM

You schedule multiple PODS on this ONE NODE:
  ├─ Pod 1: Uses GPU 1, 8 CPUs, 64GB RAM
  ├─ Pod 2: Uses GPU 2, 8 CPUs, 64GB RAM
  └─ Pod 3: Uses 16 CPUs, 128GB RAM (no GPU)

Multiple pods share the same node (bin-packing)
```

### Kip Model (Virtual Kubelet)

**This is the key difference - Kip creates ONE virtual node, but EACH pod gets its OWN AWS instance!**
```
Kip Virtual Node (not a real machine!)
  Advertises capacity: 200 CPUs, 800GB RAM, 50 pods
  ↓
  This is just an API object in Kubernetes
  ↓
When you create a pod scheduled on this virtual node:
  ↓
Kip creates ONE AWS EC2 INSTANCE per pod
  ↓
Pod 1 → AWS Instance 1 (g4dn.xlarge - dedicated to this pod)
Pod 2 → AWS Instance 2 (p3.2xlarge - dedicated to this pod)
Pod 3 → AWS Instance 3 (t3.large - dedicated to this pod)
The mapping is: 1 Pod = 1 AWS EC2 Instance

Example
You submit 5 GPU jobs:

yaml
# Job 1
apiVersion: v1
kind: Pod
metadata:
  name: training-job-1
spec:
  nodeSelector:
    type: virtual-kubelet
  containers:
  - name: train
    resources:
      limits:
        nvidia.com/gpu: 1
        cpu: "4"
        memory: "16Gi"

# Job 2
apiVersion: v1
kind: Pod
metadata:
  name: training-job-2
spec:
  nodeSelector:
    type: virtual-kubelet
  containers:
  - name: train
    resources:
      limits:
        nvidia.com/gpu: 1
        cpu: "8"
        memory: "32Gi"

# ... 3 more pods ...
```

**What Kip does:**
```
Pod training-job-1 scheduled
  → Kip creates AWS instance: g4dn.xlarge (4 vCPU, 16GB, 1x T4 GPU)
  → Instance ID: i-abc123
  → Pod runs on this instance

Pod training-job-2 scheduled
  → Kip creates AWS instance: g4dn.2xlarge (8 vCPU, 32GB, 1x T4 GPU)
  → Instance ID: i-def456
  → Pod runs on this instance

... etc for all 5 pods ...

Result: 5 pods = 5 separate AWS EC2 instances
```

**When pods finish:**
```
Pod training-job-1 completes
  → Kip terminates AWS instance i-abc123
  → You stop paying for it

Pod training-job-2 completes
  → Kip terminates AWS instance i-def456
  → You stop paying for it
How to Control Number of AWS Instances
You control it by controlling the number of PODS, not Kip configuration.

Example: Want to run 10 parallel training jobs on AWS?

yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: parallel-training
spec:
  parallelism: 10        # Run 10 pods in parallel
  completions: 10        # Need 10 total completions
  
  template:
    spec:
      nodeSelector:
        type: virtual-kubelet
      containers:
      - name: training
        resources:
          limits:
            nvidia.com/gpu: 1
Result: Kip creates 10 AWS instances (one per pod)

Example: Want to limit to max 5 concurrent AWS instances?

yaml
spec:
  parallelism: 5         # Only 5 at a time
  completions: 20        # But 20 total jobs
Result: Kip creates 5 instances, as they finish, creates more, until 20 total jobs complete

The Kip "Virtual Node" Capacity
In your Kip config, you set the advertised capacity:

yaml
capacity:
  cpu: "200"        # Total virtual capacity
  memory: "800Gi"
  pods: "50"        # Max 50 concurrent pods
What this means:

Kubernetes thinks there's a node with 200 CPUs available
It will schedule up to 50 pods on this "node"
Each pod becomes a separate AWS instance
The 200 CPUs is just a limit, not actual hardware
Why set limits?

Cost control: Max 50 pods = max 50 AWS instances = maximum bill
Quota limits: Your AWS account may have EC2 instance limits
Sanity check: Prevents someone accidentally launching 1000 instances
Practical Example
Your Kip config says:

yaml
capacity:
  pods: "20"  # Max 20 concurrent AWS instances
You submit:

bash
kubectl apply -f job-with-100-replicas.yaml
# Job has parallelism: 100
```

**What happens:**
```
Kubernetes scheduler tries to place 100 pods
  ↓
Only 20 can fit on the Kip virtual node (capacity limit)
  ↓
20 pods scheduled → 20 AWS instances created
  ↓
Remaining 80 pods in "Pending" state (waiting for capacity)
  ↓
As pods complete, new pods get scheduled
  ↓
Eventually all 100 jobs complete, but only 20 at a time
```

**Your AWS bill:** Maximum 20 instances at once

Option 4: Resource Quotas Per Namespace
Control maximum AWS spend per lab using Kubernetes quotas:

yaml
# sdsu-cs-research namespace quota
apiVersion: v1
kind: ResourceQuota
metadata:
  name: aws-burst-quota
  namespace: sdsu-cs-research
spec:
  hard:
    # Limit concurrent AWS pods
    count/pods.kip: "10"  # Max 10 AWS instances at once
  
  # Apply only to pods targeting Kip
  scopeSelector:
    matchExpressions:
    - operator: In
      scopeName: PriorityClass
      values: ["aws-burst"]

---
# sdsu-bio-research namespace quota
apiVersion: v1
kind: ResourceQuota
metadata:
  name: aws-burst-quota
  namespace: sdsu-bio-research
spec:
  hard:
    count/pods.kip: "5"  # Bio gets fewer slots
```

**Result:**
- CS can run max 10 concurrent AWS instances
- Bio can run max 5 concurrent AWS instances
- Prevents one lab from monopolizing capacity

**Pros:**
- ✅ Built-in Kubernetes feature
- ✅ Prevents runaway costs
- ✅ Fair allocation of shared capacity

**Cons:**
- ❌ Doesn't separate AWS bills
- ❌ Still requires cost allocation
